**New finding this surfaced: only 17/99 genomic gold threats are structurally reachable by grounded generation as currently designed.** `mapping_table.json` (LINDDUN Pro Table 4.1, sourced from the official tutorial) only covers 5 interaction pairs, and all of them route through a Process (`Process<->Process/DataStore/ExternalEntity`). NIST's diagrams routinely show entities and stores talking *directly* to each other with no Process step in between — something the tutorial's table simply doesn't model. Of the 97 threats with a resolved location, only 17 sit on one of the 5 valid pairs; the other 80 break down as `ExternalEntity -> DataStore` (39 — e.g. a researcher requesting a sample directly from `DNA Store`), `ExternalEntity -> ExternalEntity` (23 — e.g. `Clinician -> Patient`), `DataStore -> ExternalEntity` (17), and `DataStore -> DataStore` (1). All 80 are skipped by `generate.py`'s `if not ctx.valid: continue`, no matter how good the model is. This is a real, structural coverage ceiling, not a prompt-tuning problem, and it's broader than just "human-to-human flows" — see "Open items" below for the decision this raises for Week 4.

**Verified this against the actual tutorial PDF, not just this repo's paraphrase of it.** Fetched `downloads.linddun.org/tutorials/pro/v0/tutorial.pdf` directly and read page 18 (Table 4.1). Confirmed `mapping_table.json` is a complete, faithful transcription — the tutorial genuinely defines only those 5 rows; this is not a gap introduced during Week 1's transcription. The table's caption states verbatim: *"Note that invalid DFD element combinations (such as DataStore-flow-DataStore or ExternalEntity-flow-ExternalEntity) are not included in this table."* `ExternalEntity -> DataStore`/`DataStore -> ExternalEntity` aren't named in that sentence but are excluded for the identical underlying reason: **every one of the 5 valid rows has a Process on at least one side.** A Data Store is inert (something has to actively read/write it — a Process); an External Entity is defined as outside the system under analysis (two of them interacting isn't system behavior to examine). LINDDUN Pro's elicitation is built around finding privacy problems in what a system's *logic* does, so it only defines applicability for interactions where such logic — a Process — is actually present. NIST's genomic diagrams break that assumption because they layer LINDDUN onto **PANOPTIC**, a broader sociotechnical framework that treats physical/human-procedural exchanges (a physical sample handoff, a researcher opening a freezer, a counselor meeting a patient in person) as first-class dataflows worth threat-modeling too, without requiring a mediating Process — appropriate for genomic data, where a lot of the real privacy risk lives exactly at those unmediated, physical/human touchpoints. This confirmation is recorded in `knowledge_base/linddun/mapping_table.json`'s own `_meta.verified_against_source_pdf` so it doesn't need re-litigating later.

**Generation pipeline built** (`generation/`):
- `schema.py` — `GeneratedThreat` dataclass mirroring the gold-standard shape plus the abstract's citation triple (`tree_node`, `originator_id` as the location citation, `regulatory_citation`), an `uncertainty_note` field so the model can flag low confidence instead of asserting, and a Claude/OpenAI-agnostic tool-call JSON schema (`THREAT_TOOL_SCHEMA`) that forces structured output instead of free-text parsing.
- `prompt.py` — grounded prompts reuse `interaction_context.py`'s applicable-types/tree-nodes block plus top regulatory retrieval hits for the flow; ungrounded prompts (the ablation baseline) give only the bare flow/element info, so any citation the model produces comes from its own training knowledge, not this repo's KB.
- `generate.py` — drives one prompt per DFD flow, grounded or ungrounded, and persists results to `storage/generated/<scenario>_<grounded|ungrounded>.json`.
- `llm_backend.py` — **pluggable provider backend** (added on request, beyond the original plan): `AnthropicBackend` and `OpenAIBackend` (the latter also covers any OpenAI-compatible `/chat/completions` endpoint — Groq, Together, Ollama, etc. — via `OPENAI_BASE_URL`), selected by `LLM_PROVIDER` in `.env` or `--provider` on the CLI. `generate.py` never talks to a vendor SDK directly, mirroring the existing pluggable-embeddings pattern in `retrieval/embeddings.py`.

**Citation verifier built** (`generation/verify.py`) — the concrete implementation of "verified, not asserted." Pure data lookups, no LLM calls: `tree_node` checked against `threat_trees.json`; `threat_type` checked for applicability at the flow's element-type interaction via `mapping_table.json`; `originator_id` checked against the scenario's `dfd.json`; `regulatory_citation` independently parsed out of `regulations.md` (not the RAG chunks) and checked both for existence and for whether that provision's own `LINDDUN relevance:` annotation actually names the claimed threat type.

**Eval harness built** (`eval/`): `match.py` matches generated-to-gold threats — KidsTube by (flow id, threat type), with a stricter tier requiring exact `tree_node` agreement; genomic by (`dfd_source_id`, `dfd_destination_id`, threat type) using the new fields above, resolving the generated threat's `flow_id` against `dfd.json` (falls back to threat-type-only matching if no `dfd` is passed in, e.g. for a quick check). Gold threats with `dfd_location_confidence: "unresolved"` can never be matched, by design. `metrics.py` computes recall/precision/F1 per LINDDUN category plus citation-correctness rates. `run_eval.py` / `cli.py eval` prints the report, calling out Non-compliance and Unawareness rows specifically per the abstract's stated focus on those as hardest to automate.

**CLI wired:** `python cli.py generate --scenario kidstube [--ungrounded] [--provider anthropic|openai]` and `python cli.py eval --scenario kidstube --generated <path> [--strict]`.

**Fully tested offline, before any live call.** `tests/test_generation.py` — 139 checks (dfd.json integrity for both scenarios, genomic gold's new dfd-location fields, schema round-trip, verifier against real KB data for both valid and fabricated citations, matcher/metrics on hand-built fixtures for both scenarios' matching modes including genomic's location-based matching and unresolved-location handling, LLM-backend routing/error paths) — all passing, no API key required. `tests/test_kb.py`'s original 33 checks still pass unchanged (252 chunks, same as before — confirms `dfd.json` exclusion works and nothing regressed). ## Open items / caveats

1. **The mapping-table coverage gap (80/99 genomic threats) is the biggest open decision for Week 4.** It's broader than just human-to-human flows: of the 80 unreachable threats, 39 are `ExternalEntity -> DataStore`, 23 are `ExternalEntity -> ExternalEntity`, 17 are `DataStore -> ExternalEntity`, and 1 is `DataStore -> DataStore` — none of which `mapping_table.json`'s 5 Process-mediated rows cover. Options: (a) extend `mapping_table.json` with rows for these direct (non-Process-mediated) interactions for scenarios like genomic where NIST's PANOPTIC-style analysis models them — but this repo's mapping table is directly sourced from the official LINDDUN Pro tutorial, so adding rows not present there is a methodological choice, not just a bug fix, and would also affect KidsTube; (b) accept these interaction types as out of scope for the per-interaction elicitation methodology this repo implements, and score genomic's ceiling recall accordingly (17/99 with the current mapping table); (c) treat them as a separate elicitation pass with its own prompt strategy. Not resolved this week — flagging for advisor input alongside the other pending methodology decisions below.
2. **Regulatory-citation matching is heuristic.** `verify.py`'s `_find_provision` does digit-bounded substring matching between the model's citation string and section-number tokens parsed from `regulations.md` headings — good enough to distinguish real from fabricated citations, not authoritative legal citation parsing. Compound headings with two section numbers (e.g. `"§ 1798.110 / .115"`) are split into separate candidate ids to reduce misses.
3. **2 genomic threats (ids 20, 23) have no confidently-transcribed DFD location** (`dfd_location_confidence: "unresolved"`) and 4 more (18, 19, 26, 27) are `"low"` confidence — a locally-repeated "de-identification" pattern in Figure 11 that didn't cleanly disambiguate even after cross-referencing Figure 20 (see `scripts/build_genomic_dfd.py`'s `GOLD_ID_ROW_OVERRIDE` comments for the full reasoning per id). These are excluded from location-based matching rather than guessed.
4. **`cli.py ask` remains Anthropic-only.** The new pluggable backend only covers the generation path (`cli.py generate`); extending `ask` similarly would be a small follow-up if wanted.
