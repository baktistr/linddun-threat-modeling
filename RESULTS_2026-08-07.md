# Results 2026-08-07 — the source-arm flow-count anomaly, bisected and resolved

`RESULTS_2026-07-28.md` §5 flagged a blocking anomaly: the source→DFD `llm` arm produced
**36 flows** in the model sweep against **107 / 110 / 115** in Week 10's three runs of the *same*
arm and the *same* model (gpt-5.4), and until explained no source-arm number was citable. The
suspected cause was the `max_completion_tokens` fix made while wiring the sweep.

**Resolution: the anomaly does not reproduce. Two fresh runs of the committed code land at
111 and 109 flows — inside Week 10's range. The sweep's 36-flow derivation is a one-off from a
working tree whose exact state was never committed, and is retired as unrepresentative.**

---

## 1. The suspect is exonerated

The `max_completion_tokens` fix (`WEEK12_REPORT.md`, fixed "while wiring the sweep") changed
**`OpenAIBackend`** — which accepted `max_tokens` and never sent it. But every run in question,
Week 10 and sweep alike, went through **`AzureFoundryBackend`**, which has sent
`max_completion_tokens=max_tokens` since it was written (verified at `38e9913`, the Week 10
commit). `SYNTHESIS_MAX_TOKENS` was 8000 in both eras. The budget path is byte-identical across
the two measurements; it cannot be the cause.

## 2. Every internal input is byte-identical

Verified by direct diff between `38e9913` and HEAD:

| input to the flows call | Week 10 → HEAD |
|---|---|
| `_elements_prompt` / `_flows_prompt` | identical |
| `DFD_ELEMENTS_TOOL_SCHEMA` / `DFD_FLOWS_TOOL_SCHEMA` | identical |
| `_accept_flows` (acceptance filter) | identical |
| fact snapshot `adapters/data/kidstube_code_facts.json` | same file, committed *in* `38e9913` (492 facts, KidsTube-PE `8e98a1f`) |
| token budget (Azure, `max_completion_tokens`) | 8000 both eras |
| `AZURE_AI_API_VERSION` | `2024-12-01-preview` both eras |

All four runs' provenance cites only fact ids inside the snapshot (Week 10 runs: 281/287/242
distinct ids, 0 outside; sweep run: 275, 0 outside), so the fact universe never drifted. The only
code change is the `model=` override threading and `_meta` recording — metadata, not behavior.

Two hypotheses this rules out alongside the budget: no truncation (the 36-flow run's last flow
completes cleanly, tail descriptions as long as head, zero flows rejected) and no acceptance-filter
effect (`rejected_flows: []` in every run, both eras).

## 3. What the sweep actually ran is unreconstructable

At `d29b062` — the commit that recorded the sweep artifacts — `run_model_sweep.py` calls
`synthesize_llm(..., model=model)`, but that commit's `synthesize_llm` **has no `model`
parameter**. Run as committed, the sweep would have crashed with a `TypeError`. It did not crash,
so it ran from a working tree containing the override threading that was only committed later
(`013c066`: "missed from the sweep commit"). The runtime tree state of the sweep's source runs is
therefore not recoverable from git.

## 4. The reproduction — Week 10's behavior is the stable one

Two fresh derivations, 2026-08-07, committed code at `f322ad2`, same 492-fact snapshot, Azure
gpt-5.4 with the `model=` override (the sweep's exact entry path):

| run | elements | flows | rejected | wall time |
|---|---:|---:|---:|---:|
| Week 10 run1–3 | 15 / 15 / 12 | **107 / 110 / 115** | 0 | — |
| sweep `source_llm_gpt-5-4` | 14 | **36** | 0 | — |
| reproduction run1 (today) | 16 | **111** | 0 | 60s |
| reproduction run2 (today) | 15 | **109** | 0 | 57s |

Artifacts: `storage/derived/kidstube_llm_reproduction_run{1,2}.json`. Structurally the sweep run
is a normal gpt-5.4 run (same fields, same `uncertainty_note` usage present in the schema since
Week 10) — it is the *count* that is the outlier: the five conforming runs span 107–115, and 36
is nowhere near that band.

## 5. What this unblocks, retires, and leaves standing

- **Week 10's `llm`-arm numbers stand** (`RESULTS_2026-07-21.md` §2). The behavior they measured
  is reproducible today through the committed code.
- **The sweep row `source_llm_gpt-5-4` is retired as unrepresentative** — its 36-flow DFD, and
  therefore its downstream threat numbers (P 0.04 / R 0.27), measure generation over an outlier
  derivation produced by an uncommitted tree. It should not be cited as gpt-5.4's source-arm
  behavior.
- **The other two sweep source rows (gpt-4o-mini 13 flows, grok-4.3 18 flows) are NOT implicated.**
  They have no Week 10 baseline to conflict with, and terse output is consistent with those
  models' measured dispositions. Their standing caveat is the original one — evaluation attrition
  (only 23 / 13 of 41 gold threats re-anchor), not this anomaly.
- **Left standing:** deriving 110 flows means generating threats over 110 flows — one call per
  flow. A citable gpt-5.4 source-arm condition needs that spend (~110 generation calls per run)
  before the retired row can be replaced.

## 6. Method note

The bisection that worked here was archaeology, not re-running: diff the exact prompt, schema,
filter, input file, and budget between the two commits *before* paying for a live test, and only
then reproduce. The live test (4 calls) settled in two runs what the code diff had already
narrowed to "environment or sampling". The unreconstructable-tree finding is the process lesson:
**experiment artifacts recorded in a commit whose code could not have produced them** are exactly
what `storage/RUNS.md` exists to prevent — the sweep harness should refuse to run from a dirty
working tree, or at minimum record `git describe --dirty` into `_meta`.

## Reproducing

```bash
PYTHONPATH=. python3 - <<'EOF'
import json, config
from adapters.schema import CodeFact
from adapters.synthesize import synthesize_llm
raw = json.loads((config.ROOT/"adapters"/"data"/"kidstube_code_facts.json").read_text())
facts = [CodeFact.from_dict(f) for f in raw["facts"]]
dfd = synthesize_llm(facts, provider="azure", model="gpt-5.4", scenario_name="kidstube")
print(len(dfd["elements"]), "elements,", len(dfd["flows"]), "flows")
EOF
```
