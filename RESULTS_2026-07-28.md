# Results 2026-07-28 — three models × three inputs, grounded

Nine live conditions: **gpt-5.4 / gpt-4o-mini / grok-4.3** (all Azure, one endpoint, three
deployment names) × **hand-authored DFD / DFD image / source code**, all in `grounded` mode
against KidsTube's 41-threat gold standard.

Artifacts: `storage/derived/kidstube/<condition>/run1/` (DFDs, per-run gold) and
`storage/generated/kidstube/<condition>/run1/` (threats, eval). Index: `storage/RUNS.md`.
Cross-condition: `storage/generated/kidstube/CONDITIONS.txt`.

**n=1 per condition.** Three separate resampling swings of ~0.05 recall were measured during this
work (below), so any gap under ~0.05 here is noise. Read this as "which effects are large",
not as a ranking.

## 2. The main finding — the input modality is a small, near-constant tax; the model is the large effect

Holding the DFD identical (`dfd_hand`) isolates threat elicitation from DFD derivation:

| model | hand DFD | from image | cost of reading the diagram |
|---|---:|---:|---:|
| gpt-5.4 | 0.83 | 0.76 | **−0.07** |
| gpt-4o-mini | 0.71 | 0.68 | **−0.03** |
| grok-4.3 | 0.54 | 0.46 | **−0.08** |

The image adapter costs 0.03–0.08 recall regardless of model strength, while the spread *between*
models on the same input is 0.29–0.30. **Choosing the model matters roughly four times more than
choosing between a hand-drawn DFD and a photograph of one.**

This also settles what grok-4.3's weak image score meant. At 0.46 from the image it looked like a
vision deficit; the control shows it starts at 0.54 with a perfect DFD handed to it, and pays the
same ordinary image tax on top. Its deficit is threat elicitation, not diagram reading.

---

## 3. Threat volume is a fixed model disposition, and it drives the P/R trade

| model | threats: hand / image / source |
|---|---|
| gpt-5.4 | 137 / 116 / 239 |
| gpt-4o-mini | 83 / 81 / 62 |
| grok-4.3 | 55 / 55 / 61 |

grok-4.3 emitted **exactly 55** from both the hand DFD and the image; gpt-4o-mini 83 and 81. Volume
is a property of the model, not of what it was shown. Recall and precision track it directly —
gpt-5.4 floods and buys recall with precision (137 threats, R 0.83, P 0.25); grok-4.3 is terse and
does the reverse (55, R 0.54, P 0.40).

**On F1 the two smaller models beat gpt-5.4 in every single condition.** Since all precision here
is an automated lower bound (every unmatched threat is counted a false positive, and no scenario
has been through manual adjudication), that ordering is exactly the one manual FP adjudication
would be most likely to overturn — gpt-5.4 has 103–227 unmatched threats whose real status is
unknown.

## 4. Citation validity — high, but NOT universal

Eight of nine conditions score **1.00** on every axis (`node_valid`, `type_applicable`,
`location_valid`). The exception:

- **`dfd_hand_gpt-4o-mini`: 0.99.** One threat of 83 cited `threat_type "Uc"` with
  `tree_node "U.1"`. `Uc` is not a LINDDUN type; the model invented a category code. Caught
  deterministically by `generation/verify.py` — `node_valid` 0.99, `type_applicable` 0.99,
  `location_valid` 1.00.

This is the first citation failure the project has recorded in grounded mode, and it matters for
how the claim is worded. Grounded mode's guarantee is **structural but not absolute**: the
deterministic mapping-table lookup supplies only valid nodes, yet the model can still emit a type
outside the supplied set, and it took a smaller model to surface it. The honest statement is that
grounded citation validity is 1.00 across three models and three input modalities *except for a
single invented type code in 83 threats*, and that the verifier caught it rather than the pipeline
trusting it — which is the actual point.

---

## 5. Source-code input underperforms both other inputs, and its evaluation is fragile

Every source condition scores far below the same model's hand and image runs. Two causes, and they
must not be conflated:

1. **Real recall loss.** The adapter models the system at a different granularity, so gold threats
   have no counterpart flow.
2. **Evaluation attrition.** Only 17 / 23 / 13 of 41 gold threats re-anchor at all. The rest become
   `unresolved_location` and are unmatchable by construction.

gpt-5.4's source run is the extreme: 239 generated threats for 12 true positives (P 0.05). Its DFD
has 36 flows against the hand DFD's 17, so it generates over a system model that is both larger and
misaligned with the gold.

**Unexplained and blocking:** the source arm produced **36 / 13 / 18** flows here, against
**107 / 110 / 115** in Week 10's three runs of the *same* arm and the *same* model (gpt-5.4). That is
far outside any previously observed variance and is not explained. Until it is, no source-arm number
in this report should be cited.

## 6. Two evaluation bugs found and fixed during this work

**The flow-anchor regex assumed a `DF` prefix.** `eval/match.py`'s `FLOW_ID_RE` was
`\[(DF\d+)\]`. gpt-4o-mini's source-derived DFD numbered its flows `F1..F13`; the gold was
re-anchored correctly to `EE1-P1 [F1]`, and then the matcher could not read the gold the pipeline
had just written. All 41 threats fell to `unresolved_location` and the condition reported a
confident **0.00** that read as a model failure. Nothing enforces the `DF` convention —
`adapters/schema.py` only *describes* it — so the reader was what had to give. Broadened to
`\[([A-Za-z]*\d+)\]`; verified byte-identical output on all 10 previously committed eval reports;
that condition's real score is 0.19 / 0.29 / 0.23.

**The run index averaged an unscorable run as 0.00.** `summarize_runs.py` reported that same
condition as `0.00 / 0.00 / 0.00` with no caveat. It now detects `unresolved_location == n_gold`
and flags the run **UNSCORABLE**, excluding it from score means while still counting its citation
validity and volume (which do not depend on gold anchoring).

Both are the same failure shape the project refuses everywhere else: a confident zero where the
honest answer is "this cannot be measured".

## 7. Measured run-to-run variance (why n=1 is not a comparison)

| what | run A | run B | Δ |
|---|---:|---:|---:|
| `image` / gpt-5.4, recall | 0.71 | 0.76 | 0.05 |
| `dfd_hand` / gpt-5.4, recall (vs Week 6 baseline) | 0.78 | 0.83 | 0.05 |
| Week 10 `llm` arm, DFD flow recall (n=3, one model) | 0.33 | 0.87 | 0.54 |

Three independent measurements, ~0.05 at the threat level and far larger at the DFD level. So in
§1: gpt-5.4 vs gpt-4o-mini on the image (0.76 vs 0.68) is only marginally outside noise; both
against grok-4.3 (0.46) is safely real. **Making the model comparison publishable requires
`--runs 3`, which triples the spend.**

## 8. Caveats

1. **n=1 everywhere.** See §7.
2. **The DFD image is synthetic** — a matplotlib render of the very `dfd.json` it is scored
   against. A ceiling measurement, not evidence about a Visio export or a photographed whiteboard.
   The original KidsTube HW2 diagram remains the fixture worth recovering.
3. **All precision is an automated lower bound.** No scenario has been through manual FP
   adjudication anywhere in the project; the 86-entry worklist at
   `storage/adjudication/kidstube_grounded.json` has been unlabelled since 2026-07-16.
4. **Source-arm flow counts are unexplained** (§5).
5. **One scenario only.** Everything here is KidsTube; nothing tests whether these orderings hold
   on Smart Home, Family Location, or genomic.
